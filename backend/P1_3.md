# P1.3 — Persistent sessions and conversation history

Implemented November 4, 2026. This report describes repository changes and
isolated test results. No development/production database migration was applied.

Subsequent local deployment and the service-category audit are documented in
[P1_3_DEPLOYMENT_AND_AGGREGATION_REPORT.md](../P1_3_DEPLOYMENT_AND_AGGREGATION_REPORT.md).
That follow-up applied migrations to the existing local database and verified
live-model requests, application restart recovery and the actual browser UI.
The results below remain the original implementation results.

## Architectural assessment

The existing `Agent` compiled a request-local LangGraph without a checkpointer
or `thread_id`. Its `LocationConversations` controller held `PendingRequest`
objects in a bounded, process-local dictionary with locks, revision checks and
30-minute expiry. These objects already held proposed addresses, resolved pins,
radius, offset-aware interval/timezone, preferences, validated plans and filters.
The vanilla JavaScript frontend held only its latest response in memory. The
coordinate endpoint accepted a compatibility `conversation_id` but did not use
it for memory. There was no durable message history or cross-restart state.

PostgreSQL/PostGIS, psycopg, reader-role enforcement, SQL migration files, and
mocked-model/disposable-PostGIS testing were already present. There is no
authentication layer. P1.3 reuses these components; ingestion, historical
geocoding, SQL functions, evidence arithmetic and verification are unchanged.

## Implementation and state boundaries

`ConversationRunner` adds a small outer LangGraph with one turn node that calls
the existing analysis graph. The official `AsyncPostgresSaver` stores this outer
graph under `thread_id=session_id`; application IDs are random UUID hex strings.
See the [official AsyncPostgresSaver reference](https://reference.langchain.com/python/langgraph.checkpoint.postgres/aio/AsyncPostgresSaver).
The new dependency is `langgraph-checkpoint-postgres>=3.2,<4`, tested with 3.2.0,
LangGraph 1.2.18, checkpoint 4.3.1 and psycopg 3.3.6. It brings the official
psycopg pool dependency. Serialization is provided by LangGraph, without pickle
fallback or a custom checkpointer. Checkpoint payloads contain ordinary JSON
application fields; runtime locks, database connections, credentials and clients
are excluded. Saved application fields are revalidated on restoration.

Each completed turn saves user/assistant messages, full response payloads with
original evidence/query IDs, the pending address workflow, and separately typed
query context. That context contains authoritative pins, radius, interval and
timezone, datasets/preferences, validated plan, filters and supporting quotes.
Pending address/candidate confirmations survive restarts without reinterpreting
or re-geocoding confirmed data. Revision checks remain in effect. Persistent
sessions have no process-local TTL or 200-session capacity limit.

The inner graph explicitly opts out of inherited checkpointing because it holds
live request-local objects. The outer invocation awaits its checkpoint tasks
before returning. Saving occurs at conversation-turn boundaries; interrupted
analyses are not resumed automatically in the middle of an SQL/LLM operation.
The last completed turn remains recoverable. Retrying an interrupted analysis
can rerun read-only tools; exactly-once request execution is not promised.

Follow-ups use the same configured model to propose a typed patch. Only named
allowed plan leaves and explicitly quoted radius/time changes replace saved
values. Missing fields retain prior values, including unrelated filters. The
existing plan/tool argument validator runs again, followed by fresh deterministic
SQL, normalization, arithmetic, claim checks and final-response checks. The model
receives saved scope/plan, never historical numerical results as current facts.
New street addresses reenter the existing explicit confirmation/geocoding flow.
Missing or rejected scope changes yield clarification without tools.

The original service tool supports exact `service_name`/status labels; it has no
road-category taxonomy. “Only road-related complaints” therefore needs a category
clarification. “Only road-related complaints (Pothole)” can apply the explicitly
named label. The implementation does not invent a road grouping or execute an
unfiltered substitute. Intent/quote interpretation still depends on the model;
mocked tests do not establish live-model semantic accuracy.

The deployment follow-up adds optional `service_names` for a validated union of
exact labels, using a new 10-argument overload that delegates to the original
9-argument function. `GET /api/v1/tools/service-categories` discovers canonical
stored labels. Broad road requests present available interpretations without
automatically including ambiguous categories; explicit lists run fresh SQL.

## Database setup and migrations

The runtime SQL tools continue to use only `AGENT_DATABASE_URL`, a restricted
reader. Persistence uses **`SESSION_DATABASE_URL`**, a separate writer with no
dataset write/admin memberships. Neither falls back to `DATABASE_URL` or the
Docker administrator password. Optional **`SESSION_SETUP_DATABASE_URL`** is read
only by the explicit migration command for schema-owner credentials. Repository
`.env` precedence follows the existing loader; real credentials remain local.

First, an administrator reviews `sql/session_history.sql` and creates a separate
runtime login, using a password prompt rather than committing passwords:

```sql
CREATE ROLE citylens_sessions LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE
    NOREPLICATION NOBYPASSRLS;
\password citylens_sessions
```

Set the runtime session URL locally and supply a schema-owner connection through
`SESSION_SETUP_DATABASE_URL` when migrating. Then, from the repository root:

```powershell
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt
.\.venv\Scripts\python.exe -m backend.scripts.setup_sessions
```

This explicitly creates `citylens.sessions` and its recent-activity index, creates
`citylens_checkpoints`, and calls the official saver's `setup()` to apply/version
its checkpoint migrations. It does not call `db.py init` or alter source tables.
The checkpoint connection uses `search_path=citylens_checkpoints`, autocommit,
dictionary rows and the officially recommended prepare threshold. Repeat the
command after compatible package upgrades. Then grant runtime CRUD only:

```sql
GRANT USAGE ON SCHEMA citylens, citylens_checkpoints TO citylens_sessions;
GRANT SELECT, INSERT, UPDATE, DELETE ON citylens.sessions TO citylens_sessions;
GRANT SELECT, INSERT, UPDATE, DELETE ON citylens_checkpoints.checkpoints,
    citylens_checkpoints.checkpoint_blobs, citylens_checkpoints.checkpoint_writes
    TO citylens_sessions;
GRANT SELECT ON citylens_checkpoints.checkpoint_migrations TO citylens_sessions;
```

Reapply the table grants after a migration creates new checkpoint tables. Review
existing PUBLIC/inherited privileges separately; do not grant the session login
membership in the SQL reader, source writer or administrator roles. The server
does not run DDL automatically and verifies required tables at startup.

`citylens.sessions` contains `session_id` (primary key), `title` (1–100 characters),
`created_at` and `updated_at` (timestamptz). LangGraph manages its own `checkpoints`,
`checkpoint_blobs`, `checkpoint_writes`, and checkpoint migration bookkeeping in
`citylens_checkpoints`; their definitions are not reimplemented in application SQL.

The application owns a bounded async pool and closes it in FastAPI's lifespan.
Each turn, read or deletion holds a PostgreSQL advisory lock for that session,
across workers, without a long transaction during model/tool work. The saver
uses that same checked-out connection, avoiding nested pool acquisition. Busy
sessions return HTTP 409. Deletion uses official `adelete_thread()` plus metadata
deletion in a single database transaction. Missing/deleted IDs return HTTP 404
and cannot silently create a replacement conversation.

Start on Windows with the included selector-loop launcher; psycopg async does
not support the Windows Proactor loop used by some Uvicorn versions:

```powershell
.\.venv\Scripts\python.exe -m backend.scripts.serve --port 8000
```

The launcher also works on other operating systems. If persistence is not
configured, legacy query/address endpoints remain usable, session endpoints
return 503, and the UI clearly states that requests are not saved.

## API contracts

| Endpoint | Contract |
| --- | --- |
| `POST /api/v1/sessions` | Optional `{ "title": "..." }`; 201 with metadata |
| `GET /api/v1/sessions?limit=50&offset=0` | Metadata array ordered by `updated_at DESC`; limit 1–100 |
| `GET /api/v1/sessions/{session_id}` | Metadata, messages, query_context, latest_response, response_kind |
| `DELETE /api/v1/sessions/{session_id}` | 204; deletes metadata, checkpoints, blobs and writes |
| `POST /api/v1/agent/chat` | Existing actions plus optional `session_id`; ask continues saved context |
| `POST /api/v1/agent/query` | Existing full coordinate request plus optional `session_id` to save it |

Create a session, then send `{ "session_id": "<returned-id>", "message": "..." }`
to the chat endpoint. Confirmations/corrections retain their existing action and
revision fields. Durable chat responses include both `session_id` and the same
value in compatibility `conversation_id`; supplying both IDs inconsistently is
rejected. With persistence enabled, a chat ask without an ID creates a saved
session automatically. Legacy process-local IDs remain usable for pending work.
Coordinate `conversation_id` keeps its legacy stateless meaning; opt in to
persistence with `session_id`. Coordinate response bodies remain unchanged.
The direct SQL-tool endpoint remains unchanged and does not add transcript turns.

Titles use deterministic whitespace normalization and first-message truncation
at 100 characters. Custom titles are retained. No model call generates titles.

## Frontend workflow

The existing HTML/CSS/JavaScript desk now lists saved conversations, newest first,
with pagination for older entries. **New Chat** creates an independent session.
Selecting a conversation restores its transcript, latest response, scope and any
pending confirmation UI. Reload restores the selected session, using only its ID
in localStorage. If browser storage is blocked, the server history still works.
Messages, pins, results and plans are never sourced from browser storage.

After coordinate analysis, **Use saved scope for this follow-up** lets question
text update saved context through the chat endpoint. Uncheck it to submit a new
full coordinate request; presets select full-request behavior. Address follow-ups
continue naturally. Saved answers can be inspected with their original evidence;
the transcript explains that new analyses query current database contents.
Deleting requires browser confirmation and removes state on the server. A stale
selected ID is cleared rather than resurrected after a refresh.

Added: `agent/sessions.py`, `agent/session_models.py`, `sql/session_history.sql`,
`scripts/setup_sessions.py`, `scripts/serve.py`, `agent_tests/test_sessions.py`,
`frontend/tests/sessions.test.cjs`, and this report.

Updated: `main.py`, `agent/workflow.py`, `agent/llm.py`, `agent/models.py`,
`agent/location_models.py`, `agent/settings.py`, `requirements.txt`, `.env.example`,
`frontend/app.js`, `frontend/index.html`, `frontend/styles.css`,
`frontend/tests/location-flow.test.cjs`, `README.md`, `AGENT.md`, and `EVALUATION.md`.

Endpoints are **unauthenticated**: all clients who can reach this local service
can list/read/delete all sessions. Session IDs are identifiers, not authorization.
Keep the existing local-development boundary; add real access control before a
shared deployment. No authentication framework was added. Checkpoints retain
addresses and responses; database access, backups and retention require operator
policy. There is no automatic pruning or pagination within a single transcript,
so large conversations increase storage and retrieval cost. Metadata timestamps
update after checkpoint completion; a crash between those writes can leave
recent-activity ordering stale while the completed conversation remains available.
Live-model interpretation accuracy and full browser visual QA remain unverified.
