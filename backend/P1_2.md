# P1.2 — Confirmed addresses to verified analysis

Open `http://127.0.0.1:8000/` after starting or restarting FastAPI from the
repository root:

```powershell
.\.venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

Use the existing root `.env` configuration (`OPENAI_API_KEY`, `OPENAI_MODEL`,
restricted-reader `AGENT_DATABASE_URL`). No new dependency or API credential
is required. Normal frontend questions use the configured OpenAI model;
confirming a proposed address permits free Census requests and, only after a
legitimate no-match, SanGIS Address Points requests. No live OpenAI call was made
during implementation. The later [36-address provider benchmark](verification/geocoding_benchmark/REPORT.md)
uses actual public-provider responses, separately from mocked workflow tests.

## Frontend workflow

The default location mode accepts street addresses inside a question, for example:

> Compare pothole complaints near 9000 Regents Driev and 9500 Gilman Drive within 800 meters over the past six months.

The same configured model extracts one or two proposed addresses, a typed analysis
plan, radius, and offset-aware dates. Its instructions support conventional
abbreviations, confident suffix typo corrections, case/spacing and omitted San
Diego/CA locality. No separate fuzzy matcher or coordinate generation is used.
Explicit question conditions override UI fallback conditions; relative dates
use the current Los Angeles reference time. If no interval can be established,
the application requests clarification rather than inventing one.

Before any geocoding, the review card shows proposed addresses, actual radius/
dates, and the proposed plan/filters. **These are interpretations, not verified
geographic addresses.** Use Confirm, type a correction, or Cancel. Typing
“Confirmed.” works only while an address proposal is awaiting confirmation.
An unrelated “yes” starts a new interpretation and cannot execute a query.

Corrections preserve the original analytical question, saved dates/radius and
filters. The model revises addresses only; another explicit confirmation is
required. Clarification of an incomplete initial question may re-extract scope;
ordinary address confirmation does not repeat planning. Use Cancel and a new
question to change established analytical conditions.

After confirmation, each address is resolved independently with Census. Only a
legitimate Census no-match invokes the official SanGIS Address Points REST layer.
Census ambiguity, invalid results and provider failures do not trigger fallback.
House number, full street/suffix/directions, supplied ZIP, locality, finite WGS84
coordinates and the existing San Diego admission envelope are checked. ZIP and
post-direction are preserved when provided; they are not inferred. Exact USPS
token aliases are supported; no fuzzy matcher or road interpolation is added.

A unique consistent match can proceed. Multiple distinct SanGIS locations use
the existing candidate-choice state; no candidate is preselected. Exactly
coincident duplicate address points retain all source identifiers. Distinct
coordinates, ZIPs or units remain separate. Empty responses, rejected results
and provider errors remain distinguishable in `geocoding_diagnostics`. SanGIS
requests have a 15-second timeout and at most two attempts for transient failures;
truncated candidate sets fail closed. Failed resolution invites correction or
the existing coordinate mode. Manual map selection is not implemented.

Census locations retain `interpolated_address`, benchmark and TIGER metadata.
SanGIS locations retain documented placement (Structure, Entrance, Centroid,
Review or Unknown), source, APNs and other returned identifiers. Assessor
centroids are labelled `parcel_centroid`; a Structure label does not prove a
rooftop, entrance or apartment-unit position. Provider and precision appear in
the review interface. These interactive locations remain separate from the
historical collision dataset's `block_approximate` precision.

The saved plan enters the existing LangGraph tool/evidence/claim/composition
nodes using only resolved pins. Two-location plans compile identical dates,
radius, filters and duplicate policy for A and B. Pothole/category/status filters
use the existing `aggregate_service_requests` tool; an all-category counter is
not silently substituted. Unsupported extracted filters request clarification.
Existing plan validation still rejects unsupported/omitted service-filter plans.

The final answer identifies resolved addresses, scope, applied filters, counts,
differences, evidence references and limitations. Tool calls, evidence, raw JSON,
SQL replay and the original coordinate mode remain available. Manual SQL is
disabled for an unresolved address conversation; choose coordinate mode to
perform an independent explicit pin query. Counts are not neighborhood safety
scores. Coverage/freshness and interpolated locations remain limitations.

## Additive API

`POST /api/v1/agent/query` and `/api/v1/tools/run` retain their existing contracts.
`POST /api/v1/agent/chat` adds these explicit actions:

| Action | Required fields | Effect |
| --- | --- | --- |
| ask | message; optional time_range, radius_meters, preferences | Interpret only; return proposed addresses or clarification |
| correct | conversation_id, revision, message | Revise addresses, preserve analysis, require fresh confirmation |
| clarify | conversation_id, revision, message | Complete an insufficient initial interpretation |
| confirm | conversation_id, revision | Geocode a valid pending proposal; execute only after all pins resolve |
| choose_candidates | conversation_id, revision, candidate_choices | Confirm server-issued candidate IDs for every unresolved location |
| cancel | conversation_id, revision | End the pending request without further execution |

Example start:

```json
{"action":"ask","message":"Compare pothole complaints near 9000 Regents Driev and 9500 Gilman Drive within 800 meters over the past six months."}
```

Confirm using the exact `conversation_id` and `revision` returned by the server:

```json
{"action":"confirm","conversation_id":"<returned ID>","revision":1}
```

The response contains status/message, original question, proposals, saved scope/
plan, candidate choices, and resolved location metadata. A completed response
contains the existing `QueryResponse` under `result`, including tool logs/evidence.
The client cannot supply model coordinates or arbitrary candidate coordinates.
Missing, expired or stale confirmation state returns HTTP 409. Requests that
cannot establish a specific house number/street ask for clarification. Model
transport/configuration failures return an error with bounded diagnostic codes.

Sessions are process-local, limited to 200 entries and expire after 30 minutes.
Each uses an opaque ID, revision checks and a lock across the conversation turn.
Repeated/concurrent confirmation after completion returns the cached result;
it does not repeat geocoding or SQL. No new orchestration framework, database
tables, conversation migrations or writable Agent privileges were introduced.

The subsequent SanGIS milestone's combined focused suite passed **89 tests**,
with zero failures or skips. Its 36-address live comparison, recorded-response
FastAPI/real-reader SQL smoke, coordinate-disagreement statistics and remaining
limitations are documented in the [benchmark report](verification/geocoding_benchmark/REPORT.md).
Those test counts overlap the initial P1.2 suite and must not be added.

Frontend: **six scenarios passed** (three new location-flow scenarios plus the
three existing startup scenarios). Node was available through the test runtime;
it was not installed as a new project dependency.

Frontend tests cover correction/cancellation, candidate confirmation without
default selection, an unbound “yes”, plus existing configuration startup/failure/
timeout handling. The Node VM DOM harness is not a full browser visual test.

The small API smoke used model/geocoder fixtures and **real Agent-reader SQL**.
It confirmed no geocoding before confirmation, two symmetric filtered queries,
verified evidence/comparison, and unchanged collision record/location/status
counts. **Fixture pins are not actual geocodes of the example addresses.**
See [smoke output](audits/2026-11-02-p1_2-smoke.json).

Reproduce focused tests and the controlled SQL smoke:

```powershell
.\.venv\Scripts\python.exe -m pytest backend/agent_tests/test_location_flow.py -q
node frontend/tests/startup.test.cjs
node frontend/tests/location-flow.test.cjs
```

The `node` test commands require a Node.js executable. This workstation's
PowerShell did not expose one, so those same tests were run through the available
Node test runtime. Node is not required to serve or use the plain browser frontend.

## Known limits

- No paid/live model call was made. Real spelling interpretation still needs a
  user-run confirmed question with configured credentials. Public geocoder
  behavior was measured separately in the live benchmark. Proposed changes
  always need review; invalid structured output fails closed.
- Memory is not durable or shared between server processes. Use one Uvicorn
  worker; restarting the backend or reloading the page requires a new question.
  This is pending-request support, not persistent chat history.
- One or two numbered street addresses are supported. Units, intersections,
  partial street names and ambiguous components may require clarification.
- The supported region is a broad envelope, not an independently verified city
  boundary. Census interpolation and incomplete imported datasets limit analysis.
- No automatic retry/reset of historical collision geocodes, batch enrichment,
  new SQL generation or safety scoring is performed. The interactive fallback
  does not update stored collision locations or statuses.
